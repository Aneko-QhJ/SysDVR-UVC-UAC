## 实测日志能进一步说明什么

同一Mach时钟域里，两次真实BURST触发的453.402042 ms可以按实际tick精确分段：

| 区间 | 时长 |
| --- | --- |
| 第一轮实际触发至第一轮saved事件 | 156.811709 ms |
| 第一轮saved至第二轮before_intent | 293.376375 ms |
| 第二轮before_intent至实际触发 | 3.213959 ms |

各区间按tick精确相加，展示时纳秒向上取整可能相差1 ns。完整STATUS读取、校验留证、frame query及提交都发生在第二个`before_intent`之后，因此不能用这些USB操作解释之前293.376375 ms的间隔。第一轮ISO提交到回调约152 ms，第二轮相近，这也是本次453 ms触发间隔的组成部分。

封存调用链中，协调器在无inflight工作时先完整检查再进入entry；driver启动直接arm第一轮，首轮保存只更新计数、下一次poll才arm第二轮，末轮后另一次poll检查250 ms观察窗口。结合最终检查顺序，按串行调用次序推定：

| 完整检查序号 | 对应边界 | CLOCK_MONOTONIC_RAW耗时 |
| --- | --- | --- |
| 270 | 启动第一轮前 | 265.657291 ms |
| 271 | 第二轮arm前 | 287.660875 ms |
| 272 | 末轮后的观察poll前 | 288.198750 ms |
| 273/274 | finalize前/后 | 291.030750 / 274.439083 ms |
| 275/276 | 导出前/后 | 268.615083 / 268.540791 ms |

271号耗时与293.376 ms间隔接近，支持完整检查是当前轮间主要开销。序号归属由调用顺序推定，没有把RAW绝对时间与Mach事件绝对时间相减，也未证明跨时钟校准；不能把两种时长的差直接认作精确的调度或permit开销。先前268 ms数字属于导出边界，不是轮间检查。

同样，272号检查本身超过250 ms，且与接收回调使用同一串行主队列；timer标称1 ms不代表每1 ms实际运行一次。随后poll满足时间阈值，并不证明该队列在整个窗口里持续处理事件。已有成功回调和观察窗口继续保留，`callback_drain_verified`仍false。
