## 实现及约束

候选从已封存 quiet 源树复制生成，旧 189 项来源保持，新增 6 项来源，共 195 项。生成树相对 quiet 只有 8 个文件变化：main、运行 recipe、三个原保存适配器、LCP1 头及新的文件适配器两文件。工作区生产代码及旧候选未改。原型头在生成树中仅调整两处语句换行，以通过严格警告检查。

main 在 USB 初始化前取得主线程 ID 和独立随机 nonce，排他创建 `/ep0-life-<32位十六进制nonce>.bin`，固定 3968 字节。它显式分块清零整个文件、flush、检查大小、完整读回、关闭文件后 commit，再保存 LCP1 头和 PREPARED。准备失败关闭自己的额外文件系统对象，记录阶段及 SDK 返回值，main 返回 1；不会继续初始化 USB 或启动工作线程。该返回仍受原有 `__appExit` 路径约束，不证明进程实际退出。

后续记录仍为固定 40 槽、每槽 96 字节。每次写入都打开自己的文件，写槽、flush、检查文件大小、循环读回比较、关闭文件，最后 commit。支持合法短读；零读、越界读、损坏及任一错误停止记录，既不重写槽也不重试。128 字节校验及清零块使用静态存储，不把整个文件放在栈上。文件系统对象仅由 main 持有；关闭它不关闭 Core 的服务对象，也不释放 USB 或 DMA 资源。

USB 初始化前后及进入静默前有阶段记录。`g_running` 主循环内部没有 LCP1 调用、周期写、看门狗或新停止条件。离开循环后记录 cleanup、视频和音频 join 的调用及结果、exporter 身份结果；只有观察到双方 join 成功且 writer 匹配，才能读取并记录 owner 的 boot/session。工作线程主体及原 logger 未变。

主结果和 EXE3 的构建、保存及 SD 打开/创建有阶段点，保留原返回值和清理规则。主结果保存失败后仍会尝试 EXE3；EXE3 构建失败仍不调用其保存。失败 join 和诊断路径继续保留资源；正常路径仍须满足原来的两次保存及清理条件。记录器在初始化后失败，不改变这些原决策。三个保存角色为 normal、diagnostic、session-sidecar；第三个共享创建帮助函数也可用于 REL2，不能仅凭 role3 认证 EXE3。

## 证据限度

新 ELF 逐函数观察到 main 128、Prepare 240、Note 96、Context 208、Finish 64、write_once 0、transfer 144 字节持栈；编译器生成的 `ep0_lcp_note.constprop.0` 为 144 字节，quiet logger 保持 832 字节。它们是各函数的持栈，不是整条线程调用链上界。Prepare、Context 及上述 note 变体仍有间接调用未闭合；NPDM 的 main 请求 8192 不等于实际内核栈预算。本轮不认证栈安全或运行峰值。

真实文件服务语义、调用是否返回、保存耗时和设备栈余量尚未验证。虽然运行循环内没有新增写，USB 初始化前及停止阶段的额外文件操作仍改变时序，也可能阻塞。调用意图槽可能在真正 SDK 调用之前写成，最后有效槽不能当成实际最后执行点，槽缺失不能断言对应代码没有执行。

读回正确或完整槽不证明它自身 commit 成功；commit 失败后完整字节也可能存在。新记录器的文件系统 commit 可能影响同一卡上其他写入的持久化，不能用于认证主结果或 EXE3 自身提交成功。上下文槽与 EXE3 都有时才可进行内容关联；缺 EXE3 时仅能保留合法前缀及缺证结论，不能替代硬件同 run、join、清理或完整证据链认证。
