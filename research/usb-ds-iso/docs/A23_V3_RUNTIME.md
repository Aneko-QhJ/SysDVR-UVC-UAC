# A23 V3线程运行路径、日志与身份核对（2026-10-15）

本轮审查封存V3 `window-30s`最终ELF、生成源码及已安装SDK头文件。确认工作线程
TLS/reent的正常静态建立路径，修正可用栈预算，并用逐字提取的文件日志函数完成16组
ASan/UBSan模型执行。新增12项检查与此前94项相关回归全部通过，0失败、0错误、0跳过。
122份输入冻结，审查142条；原118源、七生产源、三票据及旧封存保持。

另发现接收器记录采用父输入摘要，而设备运行材料采用窗口配置后的摘要。两者不可
互换。当前先补这个关联缺口，再继续本次诊断所需的有限调用链栈核验；不扩展为通用
newlib正确性证明。没有实际设备执行、SDK调用、USB/SD访问、打包、部署或新次数。

## 栈空间的修正

最终ELF：`dfa6414af2e3ce0b3d6950103aba0126a50b22dfd09d2aba6609252939a57813`。
已安装thread.h明确：调用者提供非NULL栈时，传入大小同时容纳stack、TLS和reent。
最终threadCreate的对应分支与此一致，不能把静态数组大小全算作调用栈。

ELF内TLS有效数据8字节，按16字节对齐；`__tls_align`内容为4，而SDK取至少16。
reent为576字节，另有48字节启动参数。实际扣减640字节，启动包装函数自身再持有48字节：

| 项目 | 视频线程 | 音频线程 |
| --- | ---: | ---: |
| 静态后备数组 | 20,480 | 12,288 |
| TLS对齐区＋reent＋启动参数 | 640 | 640 |
| SDK写入Thread.stack_sz / 初始SP相对栈底 | 19,840 | 11,648 |
| 包装函数调用用户入口时剩余空间 | 19,792 | 11,600 |
| 用户线程函数自身帧 | 160 | 80 |

表中最后两行尚未扣除后续函数调用、格式化器、异常等成本。main自身帧112字节、
logger自身帧832字节也不是完整线程上界；main实际栈预算仍未核实。以上依赖SDK映射
及内核成功返回、加载重定位和ABI契约，没有测量Switch运行时峰值。

## TLS/reent建立与退出

[审查工具](../tools/audit_a23_v3_runtime.py)核对43处具体指令、GOT指针、符号大小和
完整选取函数摘要，并编译只含静态断言的AArch64对象核验reent大小和三个标准流字段
偏移。对象仅编译，不执行；不构建新的设备ELF，也不声称完整工具链已封闭冻结。

- main在`__appInit`之前执行newlibSetup，写入TLS魔数及`_impure_data`指针。
- 工作线程由threadCreate分配并清零各自576字节reent，初始化字段，继承创建者的
  stdin/stdout/stderr指针；并非所有newlib对象都独立。
- `_EntryWrap`在调用用户入口前安装该线程的reent和TLS指针。最终`__getreent`的GOT
  非零并指向`__syscall_getreent`；后者检查TLS魔数并取得对应指针，失败走fatal。
- 用户入口返回后进入threadExit，存在12槽TLS析构函数的间接调用，随后移出线程列表
  并退出。threadClose拒绝尚在列表中的线程，再解除映射/关闭句柄；正常项目退出先join。
- 这两个SDK函数中没有直接`_reclaim_reent`调用，间接析构目标仍未知。不能据此宣称
  全部reent分配已回收，也不能反推本次整数/常量字符串日志必然泄漏。

正常静态路径没有支持“工作线程未建立reent”的缺口证据。实际TLS损坏、异常退出、
SDK格式化器重入、析构回调及全程内存有效性仍未验证。

## 日志组调用与错误

main、视频、音频三个入口均可达文件logger。UAC禁用不排除音频线程启动日志，main在
启动两个线程后也有日志；不能用“仅一个线程在记录”作为未经验证的前提。

最终SDK的Open、GetSize和Write函数各自包含会话取得/释放路径；GetSize返回前释放
会话。logger自身没有包围Open→GetSize→Write→Close的锁。即使只有一个FS会话，这些
命令的串行化也不足以证明整组日志原子性。其他对象分支及Horizon文件共享/Append实际
语义没有被本轮模型替代。

[原生fixture](../tests/a23_v3_logger_fixture.c)插入封存FILE_LOGGING分支的原函数体，
格式化使用电脑libc，文件服务全部注入；两个电脑线程按受控顺序运行，各文件命令串行：

| 注入的服务策略 | 两次GetSize均返回0后的结果 |
| --- | --- |
| 允许两个写者，按显式offset写 | 两次写各4字节，最终仅BBBB，AAAA被覆盖 |
| 服务端强制原子追加 | 最终AAAABBBB，共8字节 |
| 第二次Open因共享限制失败 | 只写AAAA，第二条日志未写入 |

这些是可区分的模型结果，不是Switch文件服务的实测语义或实际并发可达性证明。
其用途是排除“单会话自然保证日志完整”的推论，不能认定原日志已经丢失或覆盖。

其余检查覆盖未挂载、空/负格式化结果、Open/GetSize/Write失败、嵌入NUL及1/510/511/
512/2048字节输入。GetSize失败跳过Write并Close；Write失败仍Close且没有调用者可见的
成功回执；长度截断到511字节。函数返回void，不能用“调用完成”认证日志内容已保存。

会话等待可使用无限等待，文件写入使用Flush且调用同步。设备窗口在视频线程第一条
启动日志前已经开始；窗口检查不能中断正在执行的同步SDK调用。没有日志耗时上界，
不能据此解释原16.395292ms超时，也不能认为30秒窗口等价于30秒内必定退出。

## 父输入摘要与运行摘要不能互换

| 标识来源 | 摘要 |
| --- | --- |
| V3审查顶层recipe_digest / 窗口recipe的parent_input_digest | `a7aed8c72e3334c083963fb734e2e62fc3d6ca5f612a4914365fd6a2388ca850` |
| window-30s recipe.input_digest / 实际ep0CandidateRecipe | `04e91db655a03fb1a61f1a92d9a1758928a868a5222ee2e9b641b82e2bddd2d7` |

生成header与ELF中两份32字节ep0CandidateRecipe逐字匹配运行摘要。当前接收器builder
从顶层recipe_digest取值，封存offline-record的recipe_sha256因而是父输入摘要。
先前runtime-next-scope中的device_recipe也引用顶层值，必须按父输入身份理解。

本轮独立`recipe-identities.json`明确保存两种身份及ELF/header证据，不改原记录。
若把旧接收器记录的recipe_sha256直接用作EXE3解码预期，会与该窗口程序写入的值不符。
这说明标识层次未接通；未执行有效采集，不能断言接收器已经因此发生运行失败。此前
收集正向模型只证明给定材料的软件比较，不证明这个构建关联已经完成。

格式化器观测值不作为当前线程上界。
