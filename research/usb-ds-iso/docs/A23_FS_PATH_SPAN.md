# 文件创建路径缓冲审查（2026-10-16，Asia/Shanghai）

承接[生命周期首次实测](A23_LIFECYCLE_FIRST_LIVE.md)：两次 SD 打开返回 0，但 diagnostic/EXE3 创建均返回 `0xD401`。本次只做离线审查和原型验证，未读写 SD、签发新次数或启动 USB 诊断。

## 已确认的代码问题

对实际已部署 ELF `737ad5…` 重新反汇编，与封存反汇编的审查结果一致；本机 libnx.a、编译器和 specs 摘要也与原构建记录匹配。已链接 `fsFsCreateFile` 在 `0xe82c` 保留调用者路径地址，在 `0xe8d4` 编入固定大小 `0x301`，在 `0xe8e0` 写入输入指针描述符，再调用 `svcSendSyncRequest`。它没有按字符串长度缩小范围，也没有在此函数中复制到完整大小的路径数组。

**SDK 提交 769 字节路径缓冲，但两条失败路径的对象都只有 96 字节。** 字符串本身不长、已经零结尾，不能保证整个提交范围可读。

| 路径 | 当前函数栈帧 | 路径相对本帧 SP | 相对 main 入口 SP 的 SDK 输入范围 |
| --- | ---: | ---: | --- |
| diagnostic / `Ep0CandidateSaveDiagnostic` | 656 | +304 | `[-480, +289)` |
| EXE3 / `Ep0ExecutionSaveJoined` | 496 | +144 | `[-480, +289)` |

`main` 固定持有 128 字节，两条路径因不同帧大小与局部偏移，最终得到相同输入范围。输入的后 289 字节在 main 入口 SP 之上。若上界就在该入口 SP，则范围越界；若上方另有至少 289 字节可读映射，则这一边界条件不会失败。**尚未测得现场映射上界，不能把模型假设写成现场地址证明。** 扩大栈下方可用空间本身也不会改变这个向上越过入口 SP 的范围。

成功的 LCP1 路径使用静态 `life_path[64]`（ELF 地址 `0xb6ba0`），同样小于 SDK 提交大小；区别是其后续 769 字节仍落在 ELF 的 RW LOAD 区间内。这可以解释为什么小对象也可能在某个布局下成功，却不能把 64 字节视为正确的 SDK 输入容量。后续修正应覆盖所有交给这些 SDK 调用的路径对象，包括 LCP1、normal、diagnostic、REL2 和 EXE3，而非只修当前失败分支。

## 原型及验证

新增独立原型 `device/ep0_fs_path_span.h`：接收调用者声明的真实可访问容量，只在源范围内寻找零结尾；无结尾或目标不足 769 字节时拒绝，不截断。成功时复制字符串并将余下整个 SDK 输入区清零，支持源与目标重叠。它只准备缓冲，不执行文件服务，也不验证文件名语义；目标须由调用者独占至同步调用返回。

原型尚未接入设备候选。独立 ARM 编译验证使用静态 769 字节暂存区，符号表确认实际对象大小 769，编译器报告原型函数本身栈帧 48 字节；这不等于完整设备调用链或实际内核栈预算已经验证。

本机保护页模型把一个已零结尾的短路径放在 96 字节可读区末尾：模拟固定 769 字节读取会触碰保护页；经完整暂存后，整段读取成功。另覆盖 0–768 的全部 769 种字符串长度、零填充、目标尾部哨兵、容量不足、源无结尾、空指针和重叠源。该模型验证输入范围问题，**没有模拟 Switch 内核，也没有复现内核返回 `0xD401`**。

8 项专项及生命周期原型、设备候选、接收器相关回归共 **50 项通过，0 失败、错误或跳过**。实测原件、收集器分析和两份现场记录保持；217 项来源包含旧 213 项原样及 4 项新增来源。

## 结论与下一步

已确认 SDK 输入跨度与路径对象容量不匹配，且两条失败调用的栈几何相同；它是解释结果文件创建失败的首要可验证假设。`0xD401` 名称为 InvalidMemoryState，但函数既可转交 SVC 错误，也可返回服务回复错误；现有记录没有区分返回分支。不能由此确认实际失败地址、错误发生层或 ISO actual 全零的原因。

下一步在新的隔离候选中统一使用完整、清零、具有明确所有权的路径缓冲，保持文件名、排他创建、读回、提交、失败不重试及原有资源保留决策。审查每个 create/open 传入范围，重新核对最终机器码、静态空间与调用链持栈，并绑定新 recipe/ELF/接收器。完成这些离线准备后，再决定新部署和唯一一次文件保存诊断；旧票据不恢复，本次不自动进入现场操作。
